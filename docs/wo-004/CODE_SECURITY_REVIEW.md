## 2. Что держится — проверено, замечаний нет

Это важно зафиксировать отдельно, чтобы исправления не сломали работающее.

- **Обхода auth на `/mcp` не найдено.** Пробы `//mcp`, `/MCP`, `/mcp/../api/project-state/...` не дали доступа к защищённым данным (401/404). Префиксная проверка `startswith("/mcp")` здесь не эксплуатируется.
- **Сравнение токена constant-time** (`secrets.compare_digest`), default-значения нет, длина <24 символов роняет старт fail-closed (`mcp_server.py:40-42`).
- **`insert_event` защищён от гонок корректно**: `BEGIN IMMEDIATE` + `UNIQUE(idempotency_key)` + `UNIQUE(source_project, source_work, version)`; вычисление `MAX(version)+1` сериализовано.
- **Stale-проверка корректна.** Сравнение `updated_at` строками безопасно: все значения проходят через `canonical_utc()` — UTC, микросекунды, суффикс `Z`, фиксированная ширина, поэтому лексикографический порядок совпадает с хронологическим.
- **Идемпотентность и conflict-семантика** ведут себя ровно как описано: тот же payload → тот же `handoff_id`, `duplicate=true`; тот же ключ с другим checksum → `HandoffConflict`, запись не создаётся.
- **Размер тела ограничен** — SDK по умолчанию режет на 4 MiB (`max_request_body_size`).
- **`PRAGMA synchronous` = FULL** (компилируемый default SQLite, код его не понижает), поэтому `durable=true` на уровне SQLite обоснован.
- **DNS-rebinding и Origin-защита активны** — проба с `Origin: https://evil.example` вернула 403 «Invalid Origin header».
- **Запись map-проекции атомарна** — временный файл + `os.replace`.

## S1 — CRITICAL: всё содержимое handoff читается без аутентификации

`BearerAuthMiddleware.__call__` (`mcp_server.py:171`) применяет проверку токена **только** к путям, начинающимся с `/mcp`. Маршрут `/api/project-state/{source_project}` (`mcp_server.py:222`), добавленный в тот же ASGI-app, возвращает полный `ProjectState` — то есть `result`, `blocker`, `owner_gate`, `next_step` по каждому зарегистрированному Work — любому вызывающему без заголовка `Authorization`.

Проба (сервер поднят с корректным токеном, запрос без единого заголовка авторизации):

```
HTTP 200, 1289 байт
  CANARY-RESULT-9f2a   -> True
  CANARY-BLOCKER-7c1d  -> True
  CANARY-GATE-3b8e     -> True
  CANARY-NEXTSTEP-1a5c -> True
```

Сегодня это удерживает только bind на `127.0.0.1`. Но `PCC_HOST` меняется переменной окружения, а весь план WO-004 — выставить сервис через Caddy. В момент публикации endpoint публикуется и этот маршрут.

`docs/SECURITY_REVIEW.md` пакета утверждает «`/mcp` отклоняет запрос без токена с HTTP 401» — это правда и одновременно неполно: проверен только один из четырёх маршрутов.

**Исправление.** Middleware должен быть default-deny: аутентифицировать всё, кроме явного allow-list (`/health`). Маршрут `/api/project-state` в production-сборке лучше удалить совсем — MCP-инструмент `get_project_state` уже покрывает эту функцию, а второй нетипизированный путь к тем же данным не нужен.

## S2 — HIGH: один статический токен даёт чтение и запись всех проектов

Нет scope, нет идентичности клиента, и в `handoff_events` нет колонки actor/source. Утечка токена коннектора ChatGPT одновременно даёт: подделку handoff от имени любого зарегистрированного Work и чтение состояния всех проектов. Восстановить по журналу, кто именно записал событие, невозможно.

Для сравнения, production PCC уже решает это: отдельная системная учётка `pcc` (`/usr/sbin/nologin`), read-only UI, и `actor` / `source` / `reason` обязательны в каждом `audit_events` и `import_runs`.

**Исправление.** Минимум — раздельные учётные данные на чтение и на запись и колонки `actor`/`source`/`reason` в событии. Перед публичной экспозицией — утверждённый OAuth boundary.

## S3 — HIGH: append-only — соглашение в коде, а не гарантия хранилища

`storage.py:34-38` описывает `handoff_events` и `delivery_attempts` как insert-only, и код это соблюдает. Само хранилище — нет.

Проба на созданной пакетом БД через обычное соединение `sqlite3`:

```
UPDATE handoff_events SET result='TAMPERED' -> SUCCEEDED, строка стала ('TAMPERED','TAMPERED')
DELETE FROM delivery_attempts             -> SUCCEEDED, удалено 1
триггеров в БД: 0
```

Production-схема PCC делает это правильно и уже содержит готовый образец: `audit_events_no_update` / `audit_events_no_delete` с `RAISE(ABORT, 'audit_events is append-only')`, плюс `pcc_write_authorized()`-guard на каждой доменной таблице, из-за которого сырое соединение вообще не может писать. Дополнительно там есть SHA-256 цепочка (`prev_hash` / `event_hash`), проверяемая `pccctl verify` и публикуемая в `/healthz` как `audit_tail_hash` — именно она делает журнал tamper-**evident**, а не только tamper-resistant.

**Исправление.** Перенести оба механизма из `pcc/schema.sql`: триггеры `RAISE(ABORT)` и хеш-цепочку. Иначе журнал WO-004 будет слабее того реестра, в который он пишет.

## S4 — HIGH: контракт запрещает лишние поля, но не секретные значения

`extra="forbid"` (`contract.py:38`) действительно не даёт незаметно протащить целый разговор, cookies или лишние ключи — это работает. Но `result` — свободный текст до 8000 символов, `blocker` и `owner_gate` — до 2000 каждый. Описание инструмента просит модель не класть туда секреты (`mcp_server.py:103`); принуждения нет.

Проба — payload принят и сохранён дословно:

```
result = "sk-proj-AAAA…AAAA https://chatgpt.com/c/68f0-secret-thread Bearer eyJhbGciOi"
-> projection_status APPLIED, в event log значение лежит как есть
```

WO прямо требует «отсутствие секретов и содержимого разговоров». Сейчас это выполнено на уровне *формы*, но не на уровне *содержимого*.

**Исправление.** Серверная fail-closed проверка значений: отклонять payload с характерными префиксами токенов (`sk-`, `ghp_`, `xox`, `Bearer ey…`), с высокоэнтропийными строками длиной свыше порога и с URL приватных тредов (`chatgpt.com/c/`, `chat.openai.com/c/`). Дёшево и закрывает заявленное требование.

## S5 — MEDIUM: receipt подтверждает доставку, которой не было

`service.py:24-35` всегда ставит `durable=True`, а `read_back_verified` вычисляет по журналу событий — при этом `projection_status` в тот же момент может быть `PENDING_RETRY`.

Инструкция самого сервера (`mcp_server.py:89-94`) говорит клиенту: «A transfer is confirmed only when `durable=true` and `read_back_verified=true`». В сценарии отказа проекции **оба поля true**, а Штаб и карта не обновились. То есть критерий подтверждения, который сервер сам диктует модели, пропускает ровно тот отказ, ради которого проекция и разделена с журналом.

Проба: `submit_handoff` при сбое проекции → `durable=true`, `read_back_verified=true`, `projection_status=PENDING_RETRY`.

**Исправление.** Критерием подтверждения сделать `projection_status == "APPLIED"` и переписать `instructions` и описание инструмента под него.

## S6 — MEDIUM: повторы без backoff, dead-letter и сигнала

`retry_pending` (`storage.py:329`) каждые 5 секунд выбирает все события без терминальной попытки и повторяет их бесконечно. Нет ни задержки, ни лимита, ни перевода в dead-letter, ни какого-либо признака отказа наружу.

Проба — 12 подряд смоделированных отказов:

```
delivery_attempts: 12 строк, все FAILED, эскалации нет
```

При устойчивом отказе это ~17 тысяч append-only строк в сутки в таблицу, которую ничто не чистит, и полностью тихая деградация: `/health` продолжает отвечать `{"status":"ok"}`.

**Исправление.** Экспоненциальный backoff, лимит попыток с переводом в dead-letter и счётчики `pending`/`failed` в `/health`, чтобы отказ был виден.

## S7 — MEDIUM: сериализация проекции работает только внутри процесса

Уточнение к формулировке: сама `projection_state` защищена корректно — стейл-проверка и upsert выполняются внутри одной транзакции `BEGIN IMMEDIATE` (`storage.py:280-316`), это межпроцессно безопасно.

Незащищена другая часть: `_write_map_projection()` (`storage.py:385`) читает БД и переписывает JSON-файл, и от параллельного процесса его прикрывает только `self._projection_lock` — обычный `threading.Lock`, локальный для процесса. Два процесса могут записать файл в обратном порядке, и карта окажется на снимке старше реального состояния при полностью корректной БД.

**Исправление.** Либо файловая блокировка вокруг записи проекции, либо жёстко зафиксировать `--workers 1` в unit-файле и записать однопроцессность как явный инвариант развёртывания (production PCC уже так и сделан).

## S8 — MEDIUM: нет версионирования схемы и пути миграции/отката

`initialize()` (`storage.py:57`) — только `CREATE TABLE IF NOT EXISTS`. `SCHEMA_VERSION = "1.0"` — константа Python, штампуется в каждую строку, но никогда не сверяется с БД; `PRAGMA user_version` не используется. Код v1, открывший БД v2, не упадёт — он молча прочитает её неправильно. Это прямо противоречит требованию WO про migration и rollback.

Production PCC решает это через таблицу `schema_meta` и отказ на неподдерживаемой версии.

**Исправление.** Хранить версию схемы в БД, сверять при старте, отказываться стартовать при несовпадении.

## S9 — LOW: fault injection для тестов в production-модуле

`fail_next_projection_for_test()`, `_test_projection_failures`, `_test_failure_lock` (`storage.py:45-46, 271-275, 378-380`) находятся в рабочем классе `HandoffStore`. Удалённо это недостижимо, но production-сборка не должна содержать переключатель «уронить следующую проекцию». Вынести в тестовый подкласс.

## S10 — LOW: сырой текст исключения в append-only таблице

`_record_attempt(handoff_id, "FAILED", str(exc)[:1000])` (`storage.py:326`). Сейчас туда попадают внутренние ошибки. Если проекция когда-нибудь начнёт касаться значений payload, это станет неотредактированным каналом копирования в журнал, который по замыслу нельзя вычистить. Классифицировать ошибки вместо сохранения сырого текста.

## D1 — BLOCKER развёртывания: за Caddy endpoint отклонит все запросы

`create_http_app` (`mcp_server.py:212-217`) передаёт `host=settings.host` и оставляет `transport_security=None`. В `mcp` 2.1.1 защита от DNS-rebinding включена по умолчанию, а `allowed_hosts` выводится из bind-адреса. За reverse-proxy заголовок `Host` будет production-именем, и он не пройдёт.

Проба с **корректным** токеном:

```
Host: 127.0.0.1:<port>     -> 200 OK
Host: waac-mcp.dedyn.io    -> 421 Invalid Host header
Host: chatgpt.com          -> 421 Invalid Host header
```

Это не уязвимость, а именно то, что механизм отработал. Но в текущей конфигурации ChatGPT не подключится вообще, и без этой пробы диагностика на живом Owner Gate заняла бы неоправданно много времени.

**Исправление.** Передавать явные `TransportSecuritySettings(allowed_hosts=[...], allowed_origins=[...])` с production-именем — не расширяя их до wildcard.

## D2 — BLOCKER: несовпадение runtime

`pyproject.toml` объявляет `requires-python = ">=3.12"`. На production VPS есть только `/usr/bin/python3.10` (Python 3.10.12), 3.11/3.12 не установлены. Сам `mcp==2.1.1` поддерживает `>=3.10`, и в коде явных зависимостей от 3.11+ не видно.

Решение владельца: либо снизить `requires-python` до `>=3.10` и прогнать полный набор проверок на 3.10, либо ставить отдельный интерпретатор 3.12. Второе добавляет на VPS новый источник пакетов и требует отдельного обоснования.
